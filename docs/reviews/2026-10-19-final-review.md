# Final principal review - 2026-10-19

Release-blocking review of SoftphonePro (C engine `native/`, PJSIP 2.17, and the app). This file tracks every finding
and its status. Native (engine) findings were fixed in the same pass; the app agent marks the app findings.

Status values: Fixed, Open, Pending (owner has not updated the row), Optional.

| ID | Severity | Area | Finding | Status | Fix / tests |
|----|----------|------|---------|--------|-------------|
| C1 | Critical | native | Remote unauthenticated DoS: `id_index_cmp` (`spc_call.c`) never advances on non-digit History-Info `index=` values (`a`, `1.a`, `-`, ...) and spins the pjsua worker thread forever (reached from `emit_incoming` -> `id_store` -> `id_parse`). | Fixed | The index is sanitised to `[0-9.]+` (otherwise treated as no index) and `id_index_cmp` is progress-safe (no progress and not at `.` -> `strcmp` fallback; iteration guard). All other parse loops audited (identity parser, `spc_presence.c` dialog-info XML and MWI, `spc_iax2_proto.c` IE loop, `spc_ws_transport.c` frame and upgrade parsing, `has_token`): each advances on every iteration. Tests: `test_caller_identity.Ident.test_raw_history_info_malformed_index_no_hang`, `test_raw_history_info_valid_order_survives_sanitising`, `test_raw_identity_fuzz_liveness` (300 INVITEs, fixed seed). Each asserts `core.ping` within 2 s and a canary INVITE still reaching `call.incoming` (ping alone is served by the request worker and cannot see a wedged pjsua thread). The malformed-index test was confirmed to fail on the pre-fix code. |
| C2 | Critical | app / Android | Exported `MainActivity` reachable by explicit intents: raw `intent.data` forwarded; `softphonepro-cli://` trusted as local CLI (dial without consent, provisioning with automation); `ACTION_ANSWER` with a guessable `callKey`; automation API started on every platform. | Fixed | `MainActivity.kt` forwards only `tel/sip/sips/callto/softphonepro`; ANSWER / OPEN_ROUTE / show-over-lockscreen require a persistent random nonce (`Prefs.intentNonce`, constant-time compare) that only our own immutable explicit PendingIntents carry (`NotificationHelper`, `bringToFront`); decline/hangup already go through the non-exported `CallActionReceiver`. Android and iOS Dart sides use `parseLink` (allowlist). `classifyLink(..., isLocal)` refuses `softphonepro-cli` unless the link was built from this process's own launch args (identity-based `isLocalLaunchLink`); unknown schemes rejected. `AutomationService` gated to macOS/Windows/Linux (`automationSupportedProvider`). `BootReceiver` now `exported=false` and checks the action. Release manifest verified with `aapt dump xmltree`: no DebugReceiver; exported = MainActivity, `SpConnectionService` (BIND_TELECOM_CONNECTION_SERVICE), `ProfileInstallReceiver` (DUMP). Emulator: CLI dial link, ANSWER `--es callKey 1` and OPEN_ROUTE without nonce are logged and ignored; `tel:600` fills the dialer, no call placed. Tests (`app/test/security_review_test.dart`): 'softphonepro-cli from the OS is rejected on every platform', 'allowed schemes pass, others are refused', 'Android link events go through the allowlist parser', 'an OS-delivered softphonepro-cli dial link places no call', '... provision link imports nothing', 'a real --dial launch argument still dials', 'does not start on TargetPlatform.android/iOS even when enabled', 'platform predicate'. |
| M1 | Major | native | Hostile WAV hangs `wav_open` on Windows / 32-bit: uint32 chunk sizes cast to `long` for `fseek(SEEK_CUR)` go negative (LLP64) and seek backwards forever (`media.fileInfo`, `call.playFile`, `call.hold{music}`). | Fixed | 64-bit offsets (`_fseeki64` / `fseeko`), file size tracked, chunks extending past EOF end the walk, 1000-chunk cap, odd-size padding handled, `fmt` size checked against the file, `data` size clamped to the real file. Tests: `test_media_files.TestHostileWav` (`test_huge_and_negative_chunk_sizes`, `test_data_chunk_sizes_lie`, `test_odd_sizes_and_padding`, `test_fmt_after_data_and_missing`, `test_truncated_headers`, `test_zero_length_data_and_zero_size_chunks`, `test_many_tiny_chunks`, `test_hostile_wav_in_call_paths`): each returns in under 1 s and leaves the engine responsive. The platform-specific hang itself cannot be reproduced on macOS/LP64; the tests cover the logic that prevented it. |
